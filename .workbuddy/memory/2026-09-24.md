## 初始化 oplus.ota 诊断 Hook 仓库

从零搭建（远端仓库原本为空）：

- LSPosed 模块 `com.a23bc.oplus.otatracer`，只监控 `com.oplus.ota`（含 `:ui` 进程）。
- 目的：定位「下载内部测试包」时 `SignVerifyUtils: ecdsaSignPki exception: No installed
  provider supports this key: (null)` → `DownloadException` / `responseCode=2304` 的成因。
  纯诊断，不改 OTA 行为、不绕过签名/完整性/权限/服务端校验。
- 架构：`HookEntry`（入口+包过滤）、`ClassHunter`（类定位）、`OtaLog`（统一 TAG
  `OplusOtaTracer` + 脱敏 + 分块）、`TracerConfig`（目标常量），以及 6 个 tracer：
  SignVerify / GetInfoThread / DownloadException / Response / KeyStore / Prefs / AppLog。
- 类定位三条路：FQCN 猜测 → `ClassLoader#loadClass` 按方法名特征匹配 → 启动 1.5s 后
  dex 扫描兜底（应对混淆）。全部 try-catch，找不到只记一次。
- 日志带 `seq=` 递增序号与 `t=+ms` 相对时间，用于判定 ecdsaSignPki 异常与 2304 的先后。

## 真机首次装机：com.oplus.ota:ui 黑屏（已修）

现象：模块启用后 OTA 的 `:ui` 进程起不来，黑屏。日志停在
`[Boot] install complete`（seq=26），之后的 `[AppLog] hook unavailable Log#d ...
(XposedHelpers$ClassNotFoundError)` 是**结果不是原因** —— `android.util.Log`
是 boot class，不可能找不到。

根因：`ClassHunter` hook 了 `ClassLoader#loadClass`，并在回调里对每个被加载的类调
`getDeclaredMethods()` 做方法名匹配。启动期类加载风暴 → 回调内触发嵌套类加载 →
应用 ClassLoader 损坏 → 之后所有 `findClass` 全失败 → UI 进程卡死。

修复（run 35957155803 已过 CI）：
- **删除 loadClass hook**，类加载本身永不 hook；反射只在后台线程做。
- 发现路径改为：FQCN 猜测（启动即解析，会逐条打 `no class xxx`）→ 3s 后关键词 dex
  扫描（后台）→ 9s 后深度扫描（后台，按方法名匹配，60 个/批 sleep 15ms，预算 15s，
  命中 SignVerifyUtils 则跳过）。
- boot class（Log / KeyStore / KeyPairGenerator / KeyFactory / Signature）改用
  `Class` 字面量 hook，不再走 `findClass` 字符串解析。
- SpTracer：廉价 key 过滤提到 `callerIsTargetApp()`（生成栈）之前；LogTracer 限流 25 行/s。
- 加心跳（每 5s 一条 `[Boot] heartbeat left=N rulesHit=[...]`，共 12 条），卡死时
  最后 seq 即卡死点；加 `TracerConfig` 三个开关用于二分定位。

教训：**在 Xposed 里 hook 类加载路径 + 回调内做反射是自毁操作**，会在启动期把宿主
ClassLoader 搞坏，且症状表现为"莫名其妙 ClassNotFoundError + 黑屏"，很难一眼看出。

## r5 日志：整条链路打开，诊断闭环

`com.oplus.ota.downloader.util.b` 全方法 hook 后的真实调用序列：

```
b.i()  getGkaReqDownloadType  读 gka_req_download=2 -> 2
b.a()  主流程(HttpsURLConnectionImpl, app, 322B 请求体, 2)
  ├─ b.k(app) -> 64 hex ; b.m(64hex) -> 32 hex
  ├─ /ts 200
  ├─ b.l(2) -> b.g(): KeyStore.containsAlias("ota_pki_attest") -> false
  │                   return 3204B base64ish（证书链/CSR）
  ├─ b.h(3204B) -> Certificate[]
  └─ b.d(p5.b)  = ecdsaSignPki，**只有一个参数**（不是 Key，内部自己取）
       ├─ getKey("ota_pki_attest") -> null
       ├─ Signature.getInstance("SHA256withECDSA")
       └─ initSign(null) -> InvalidKeyException
   b.d() return "" ; b.a() return null
   -> GetInfoThread: download denied 2304 -> DownloadException(2, 2304)
```

**两个颠覆性发现**：

1. `containsAlias("ota_pki_attest")` 返回 **false**，代码**明知不存在**却无任何分支，
   直接继续 getKey → null → initSign(null)。属 App 侧代码缺陷，不是环境异常。
2. **有证书无私钥**：b.g() 拿到 3204B 证书链（b.h() 解析为 Certificate[]），
   但 AndroidKeyStore 里没有对应私钥。
3. 全程零 `generateKeyPair`（唯一 generateKey 是
   `com.allawn.cryptography.util.KeyUtil.generateAesKey` → RsaDigitalEnvelopeUtil
   的数字信封 AES 密钥，与 PKI 无关）→ 该 EC 密钥是**外部预置**，OTA 只读取。

最终根因：设备 AndroidKeyStore 里缺少预置的 `ota_pki_attest` EC 私钥（产线写入或
SAU 下发环节没完成 / 被清过）；App 侧未处理 containsAlias=false 的情况。
2304 是本地构造（`body:null`），`/ts` 与 `/download` 均 HTTP 200。

结论已写入 README「诊断结论（已闭环，真机验证）」一节。

## 修复模式第 1 轮：密钥生成了但没进 KeyStore

```
[Repair] alias missing, generating EC key pair alias=ota_pki_attest
[Repair] generated ... pub=[com.android.org.conscrypt.OpenSSLECPublicKey EC X.509 91]
                       priv=[com.android.org.conscrypt.OpenSSLECPrivateKey EC PKCS#8 138]
[KeyStore] getKey result null          <- 依旧 null
```

判据：`encodedLen` 非 null ⇒ **不是 AndroidKeyStore 密钥**（AKS 密钥 getEncoded() 恒为 null），
而是 Conscrypt 软件密钥，`KeyPairGenerator.getInstance("EC","AndroidKeyStore")` 没拿到
keystore-backed 实现。

r7 增强：打印 `kpg.getProvider().getName()` + impl class；ECGenParameterSpec 被拒时
回退 `setKeySize(256)`；生成后自检 `containsAlias/getKey/getCertificateChain`；
并 dump KeyStore 的 alias 清单（限 30 个）看系统里到底存了什么。

r7 结果（关键）：
- `generator provider=AndroidKeyStore impl=java.security.KeyPairGenerator$Delegate`
  → **JCA Delegate 静默回退**到 Conscrypt，参数不被 AndroidKeyStore 接受。
- `[Repair] verify containsAlias=false key=null`，`chainLen=4`。
- **alias 清单**：`ota_simple_key, pki_sdk_all_bizCerts_alias_v2,
  pki_sdk_all_localKeys_alias_v2, pki_sdk_scene_data_sp_alias`
  → **PKI SDK（allawn）有自己的密钥存储**，不在 `ota_pki_attest` 下。
- 且 `getInstance("SHA256WITHECDSA")`（全大写，PKI SDK 而非 OTA）+
  `initSign(OpenSSLECPrivateKey)` **签名成功 byte[72]** ⇒ 存在一把能用的 EC 私钥，
  只是 `b.d()` 从 `getKey("ota_pki_attest")` 取不到。

r8：4 组 KeyGenParameterSpec 策略（曲线/密钥长度 × 有无 digest），每组用
`getEncoded()==null` 自检是否真进 KeyStore；都不行则**兜底注入**私钥给 getKey
（`ENABLE_KEY_INJECT`）。这是全模块唯一一处 setResult，CI 只读门禁对
`KeyRepair.java` 单独开白名单，其余文件零容忍。签名与服务
端校验不变，只补密钥材料。

## r8 结果：签名成功，服务端返回 2713（重大进展）

- 4 组策略**全部** `keystoreBacked=false` → 这台机器的 AndroidKeyStore 就是不接受这些
  KeyGenParameterSpec（可能不支持 EC 生成），只能走注入。
- 注入生效：`[Repair] injected generated private key`，
  `initSign(OpenSSLECPrivateKey)` → `sign result byte[72]` →
  **`[SignVerify] d return String(len=96)`**（此前恒为 `len=0`）。
- **服务端错误码从 2304 变成 2713**：说明请求真的带着签名发出去并被处理了，

## r10 结果：找到 2713 的真因 —— 我们的密钥抢了 SDK 的位置

完整调用链（全部未混淆，可直读）：

```

AttestationManager.generateX509
  -> generateX509V2 -> generate
  -> packParametersToCryptoEng -> packBasicAttestation -> packPublicKeyInfo
     -> AttestationUtil.createApplicationPublicKey(algorithmEnum, "ota_pki_attest")
        -> deleteKeyIfExists("ota_pki_attest")
```

即：SDK 本来要生成**带 attestation 的密钥**，我们的普通 EC 密钥抢先占了 alias，

`KeyRepair.onMissingAlias` 检测到就让位（不生成，仅记 defer）。

### r11 结果：让位成功，SDK 自己造了密钥，但 2713 不变

**body 捕获的做法（重要，别再想别的方案）**：不能包装/替换 InputStream（那是改返回值），
也不能自己提前读（会消费 app 的数据）。正确做法是：
`getInputStream` 返回时把**那个 stream 对象**记进 ThreadLocal，
然后对该 stream 的**具体类**动态 hook `read`/`close`，回调里用
`param.thisObject == TRACKED_STREAM.get()` 精确过滤，
只把 app 自己读出来的字节镜像进 ByteArrayOutputStream，EOF(-1) 或 close 时 flush。
app 读什么我们记什么，不超前、不替换。

**过滤机制复用**：`OtaLog.callerIsTargetApp()`（调用栈）+ `ResponseCodeTracer.safeUrl()`
（URL 脱敏，已改为包内可见 static 复用）+ host hint `allawntech/component-ota`，
外加 `param.thisObject == GKA_CONN.get()`（b.a 拿到的那个连接）作为 OR 条件。
不是全局无条件打 header。

坑：把 `safeUrl` 从 `CodeCallback` 内部类提到外层时漏了闭合内部类的 `}`，

- 现在（停用后）：**只有 basic**
→ device integrity 不被认可，**支持候选 A（设备完整性）**。

**但有个关键反证**：r15–r19 那几轮都是**在隐藏模块（含 Tricky Store）生效下**跑的，
PI 三绿，OTA 仍然 2713、packIdAttestation 仍 false、cryptoeng 仍 fail 4 次。
→ **Play Integrity 通过 ≠ OPPO 放行**。
OPPO 走的是自家 CryptoEng/TEE 通路，Tricky Store 骗的是 Google 那条 keybox
attestation，**两条不相干**。所以这类"骗过 PI"的手段对 OPPO 无效。

### 用户侧硬约束（上锁不可行，三条每条单独都够）
1. **刷了前置包之后打不开 fastboot** → 连操作入口都没有
2. **OPPO 对一加13 做了 ARB=1 熔断** → 回滚/降级不可逆，失败即砖
3. **电脑没有空间备份** → 连退路都没有

**结论：不要上锁。** 高风险、零退路，且多半压根操作不了。

### 定稿
客户端代码正确；服务端判 is_recruit=false 且 ID attestation 缺失；
根因指向设备完整性（BL 解锁 → CryptoEng/TEE 拒绝），但**无法从客户端直接证明**。
在当前约束下这台设备拿不到内测包。等包或推官方，二选一。

## 补充：不上锁的另一个理由（用户确认）

用户早年曾用 `KmInstallKeybox` 灌过一份泄露的 attestation keybox，原厂 keybox 被覆盖且无备份。
后果：**即使回锁 BL，Play Integrity 的 STRONG 也回不来** —— strong 需要原厂未吊销的 keybox，
回锁不能还原它。

而 OPPO OTA 那条路用的是**自家 device CA + CryptoEng**（`CertUtils.getDeviceCA/ServiceCA/RootCA`），
与 Google keybox 不是一套东西 —— 所以理论上回锁可能修 OTA，但修不了 PI strong。

综合代价：两次清机 + ARB=1 不可逆 + 打不开 fastboot + PI strong 依然没有
→ 只为一个内测包，**不上锁的结论更稳了**。

（唯一能真正恢复 strong 的路径是找回当年原始 keybox 的备份，通常存在于
/persist 或 /mnt/vendor/persist 下的 km 相关目录；若当年的整机/TWRP 备份还在，值得翻一下。）
