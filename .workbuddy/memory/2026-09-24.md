## 初始化 oplus.ota 诊断 Hook 仓库

从零搭建（远端仓库原本为空）：

- LSPosed 模块 `com.a23bc.oplus.otatracer`，只监控 `com.oplus.ota`（含 `:ui` 进程）。
- 目的：定位「下载内部测试包」时 `SignVerifyUtils: ecdsaSignPki exception: No installed
  provider supports this key: (null)` → `DownloadException` / `responseCode=2304` 的成因。
  纯诊断，不改 OTA 行为、不绕过签名/完整性/权限/服务端校验。
- 架构：`HookEntry`（入口+包过滤）、`ClassHunter`（类定位）、`OtaLog`（统一 TAG
  `OplusOtaTracer` + 脱敏 + 分块）、`TracerConfig`（目标常量），以及 6 个 tracer：
  SignVerify / GetInfoThread / DownloadException / Response / KeyStore / Prefs / AppLog。
- 类定位三条路：FQCN 猜测 → `ClassLoader#loadClass` 按方法名特征匹配 → 启动 1.5s 后
  dex 扫描兜底（应对混淆）。全部 try-catch，找不到只记一次。
- 日志带 `seq=` 递增序号与 `t=+ms` 相对时间，用于判定 ecdsaSignPki 异常与 2304 的先后。

## 环境/工具坑（本机，影响后续操作）

- **本机 git 无法创建带斜杠的分支 ref**：`refs/heads/feat/xxx` 写不进去（`git commit`
  输出成功但实际未落盘，`git log` 报 no commits）。分支名用不带斜杠的 `tracer`，
  推送时用 refspec `tracer:refs/heads/feat/ota-download-tracer` 得到远端带斜杠分支名。
- **bash 沙箱会丢弃 `.git/objects` 的写入**：commit / push 需用非沙箱模式执行；
  沙箱内 `/tmp` 与非沙箱不互通（`-F /tmp/msg.txt` 在沙箱外读不到）。
- **本机无 Android SDK**，编译走 GitHub Actions（`gh run watch`）。
- CI：`android-actions/setup-android@v3` 在当前 runner 上失败（装已废弃的 `tools` 包）。
  改用 runner 自带的 `/usr/local/lib/android/sdk` + 按需 `sdkmanager --install`
  `platforms;android-34` / `build-tools;34.0.0`；Gradle 8.2 直接下载发行版。
- CI 里有「只读性门禁」：grep `setResult|setThrowable|param.args[n]=`，需排除注释行，
  否则 HookEntry 的注释会误报。
- 产物：debug APK 自带 debug 签名可直接 `adb install`；release 是 unsigned，装不上。

## 真机首次装机：com.oplus.ota:ui 黑屏（已修）

现象：模块启用后 OTA 的 `:ui` 进程起不来，黑屏。日志停在
`[Boot] install complete`（seq=26），之后的 `[AppLog] hook unavailable Log#d ...
(XposedHelpers$ClassNotFoundError)` 是**结果不是原因** —— `android.util.Log`
是 boot class，不可能找不到。

根因：`ClassHunter` hook 了 `ClassLoader#loadClass`，并在回调里对每个被加载的类调
`getDeclaredMethods()` 做方法名匹配。启动期类加载风暴 → 回调内触发嵌套类加载 →
应用 ClassLoader 损坏 → 之后所有 `findClass` 全失败 → UI 进程卡死。

修复（run 35957155803 已过 CI）：
- **删除 loadClass hook**，类加载本身永不 hook；反射只在后台线程做。
- 发现路径改为：FQCN 猜测（启动即解析，会逐条打 `no class xxx`）→ 3s 后关键词 dex
  扫描（后台）→ 9s 后深度扫描（后台，按方法名匹配，60 个/批 sleep 15ms，预算 15s，
  命中 SignVerifyUtils 则跳过）。
- boot class（Log / KeyStore / KeyPairGenerator / KeyFactory / Signature）改用
  `Class` 字面量 hook，不再走 `findClass` 字符串解析。
- SpTracer：廉价 key 过滤提到 `callerIsTargetApp()`（生成栈）之前；LogTracer 限流 25 行/s。
- 加心跳（每 5s 一条 `[Boot] heartbeat left=N rulesHit=[...]`，共 12 条），卡死时
  最后 seq 即卡死点；加 `TracerConfig` 三个开关用于二分定位。

教训：**在 Xposed 里 hook 类加载路径 + 回调内做反射是自毁操作**，会在启动期把宿主
ClassLoader 搞坏，且症状表现为"莫名其妙 ClassNotFoundError + 黑屏"，很难一眼看出。

## 第二轮真机日志（run 35957875328 之后装的模块）

黑屏消失，心跳正常，拿到关键证据：

- 真实包名结构：`com.oplus.ota.downloader.*`（DownloadException 在
  `com.oplus.ota.downloader.DownloadException`，签名工具类在
  `com.oplus.ota.downloader.util.SignVerifyUtils`——首次只命中其内部类
  `$ByteArrayComparator`）。
- **2304 不是 HTTP 码**：同期 `[Response] responseCode=200 url=.../download?keys=[...,gkaReq]`。
  2304 出现在 `DownloadException` 的 msg：`{"body":null,"errMsg":"2304","responseCode":2304}`，
  是业务错误码（问题 F 已答）。
- **异常在请求之前**（问题 E）：`KeyStore getKey -> null` 紧跟着
  `DownloadException mCode=2 mGKACode=2304`。
- **涉及 AndroidKeyStore**（问题 D），且后面一次 `getKey` 返回
  `android.security.keystore2.AndroidKeyStoreSecretKey algorithm=AES` ——
  **用 AES 对称密钥去做 ECDSA 签名**，这就是 `No installed provider supports this
  key: (null)` 的根因方向（问题 A/B）。调用栈
  `x7.a.j -> w7.f.k -> com.oplus.ota.service.OTAService.I`。
- `gka_req_download=2`，读取点 `com.oplus.ota.downloader.util.b.i`（后台线程 `u7.a.run`）
  与 UI 线程 `x6.a`（问题 G）。
- 下载线程类名是混淆的 `u7.a`，靠类名猜不到。

第二轮修的内容：FQCN 候选补 `com.oplus.ota.downloader.*`；ClassHunter 命中内部类时
回溯外部类；深度扫描改为「目标方法真的 hook 上才算数」（markSatisfied）；
**LogTracer 的 flatten bug**——`Class[]` 被当成单个参数传给 findAndHookMethod，抛
ClassNotFoundError，导致 AppLog 回声一直没生效（这个坑和 KeyStoreTracer 之前的是
同一个，XposedHelpers 的 varargs 必须手工展开）；KeyStore alias 改打印明文；
新增 ThreadTracer（hook `Thread#start` + `ThreadPoolExecutor#execute`）定位混淆线程。

Xposed 通用坑：`XposedHelpers.findAndHookMethod` 的 varargs 不接受 `Class[]` 元素，
必须把参数类型逐个展开再追加 callback，否则报 ClassNotFoundError。

## 第三轮：用户装的是旧包，日志无新信息

13:08 的日志仍是 r2 行为（FQCN 只有 7 条旧候选、`Log#d` 仍失败、deep-scan 文案是旧版
"already resolved"）——**装机前要确认 APK 版本**，日志本身就能验伪。

但这一轮读出新结论：**2304 来自 `/ts` 接口**。时序：`/ts` 200（+8812）→ getKey null
（+8828）→ DownloadException mGKACode=2304（+8870）→ `/download` 200（+9045）。
DownloadException 早于 download 响应，所以 2304 是 `/ts` 响应体里的业务错误码
（HTTP 200 + body errMsg=2304）。`/ts` 是带签名的握手接口，所以根因仍是本地签名没做出来。

补的兜底（r4）：hook `Signature#initSign(PrivateKey)` 与 `#sign()`，**同时 hook
`java.security.Signature$Delegate`**——因为 getInstance() 返回的是 Delegate，它覆写了
这些方法，只 hook 基类不生效。签名原文不打印（describe 对 byte[] 只报长度）。
注：`Signature$Delegate#initSign` 实际报 NoSuchMethodError（Delegate 用的是
engineInitSign），但 hook 基类 `Signature#initSign` 就够——栈证明 Delegate 最终
走 `Signature.initSign(Signature.java:683)`。

## r4 日志：根因锁死（诊断目标达成）

决定性三行：

```
[KeyStore] getKey enter arg[0]="ota_pki_attest" arg[1]=null
[KeyStore] getKey result null
[KeyStore] initSign enter arg[0]=null
[KeyStore] initSign exception: java.security.InvalidKeyException:
           No installed provider supports this key: (null)
    at java.security.Signature$Delegate.chooseProvider(Signature.java:1344)
    at java.security.Signature$Delegate.engineInitSign(Signature.java:1389)
    at java.security.Signature.initSign(Signature.java:683)
    at com.oplus.ota.downloader.util.b.d(Unknown Source:47)
    at com.oplus.ota.downloader.util.b.a(Unknown Source:98)
    at u7.a.a(Unknown Source:128)
    at u7.a.run(Unknown Source:27)
```

- **根因**：AndroidKeyStore 中**没有 alias `ota_pki_attest` 的 EC 私钥**，`getKey` 返回
  null，拿 null 去 `Signature.initSign()` → InvalidKeyException。同一 KeyStore 里
  `ota_simple_key`（AES）能取到，说明 KeyStore 本身正常。
- **阴性证据**：全程**没有一次 `KeyPairGenerator.getInstance`** 调用 —— 这台设备上
  OTA 从未生成过该密钥对，只读取。
- **2304 是本地构造**（`body:null` 无服务端响应体），`/ts` 与 `/download` 都是 HTTP 200。
  上一轮"来自 /ts 响应体"的判断已作废。
